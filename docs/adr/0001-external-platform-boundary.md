# ADR-0001：外部平台不作为插件接入

- 状态：已接受
- 日期：2026-10-27
- 范围：DSH 平台 / AdapterHost / Capability 契约

## 背景

讨论是否把外部 QQ 接入项目（例如 Derpyu520/qq-bridge）作为一个
capability 插件接进我们的平台。

该类项目通常拥有：

- 自己的进程
- 自己的会话映射
- 自己的权限配置
- 自己的控制台
- 自己的调度与状态

它实际上是一个平台，而不是一个能力插件。

## 决策

### 1. 外部能力型插件

只提供输入/输出能力的插件，通过实现 capability 契约接入。

```text
外部能力
  → capability manifest
  → 薄适配层
  → 平台
```

### 2. 外部有状态服务

如果它只是“带状态的能力”（缓存、队列、任务 ID），可以有条件接入：

```text
service adapter
  + capability
  + 生命周期
  + 幂等 / 重试
```

前提是它暴露稳定的窄 API，且不要求接管我们的会话、身份、UI 或调度。

### 3. 外部平台

如果外部系统拥有自己的会话、身份、控制台、调度和生命周期，则：

```text
不把它作为 capability 插件接入
```

正确的定位是：

```text
对等平台
或
通信适配器
或
窄 API 服务
```

而不是：

```text
我们的平台
  └─ 把另一个平台塞进 capability
```

### 4. 判断规则

```text
它只提供能力           → 支持
它提供能力 + 内部状态  → 有条件支持
它拥有自己的宿主       → 不按插件支持
```

## 结论

> 外部有状态服务如果只是“带状态的能力”，可以接；
>
> 如果它已经是一个拥有自己会话、身份、UI 和调度的平台，一般不需要、也不应该作为插件接入。

> 我们支持的是“能力提供方”，不是“另一个平台”。

## 对 Derpyu qq-bridge 的定位

它不是我们的 capability 插件，也不是 `dsh-qq-bridge` 的 drop-in 替代品。

它是：

```text
一个对等的 QQ 接入平台
```

可以：

- 作为架构参考
- 作为外部网关/服务接入
- 与我们的方案共存

但不应：

- 作为一个 capability 塞进 AdapterHost
- 接管我们的 session / principal / quota
- 让它的控制台成为我们的控制面

## 影响

- 平台不为“任意外部平台”提供万能适配。
- 平台只承诺：
  - 能力契约
  - 有状态服务契约
  - 适配器契约
- 外部平台接入需要明确的边界适配，不属于通用插件机制。
